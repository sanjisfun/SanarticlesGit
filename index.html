Кратко о Git и GitHub

Git — распределённая система контроля версий. GitHub — сервис поверх Git, добавляющий веб-интерфейс, совместную работу (PR), управление задачами и интеграции. Вместе они позволяют отслеживать изменения, работать над фичами и организовать автоматизацию от тестов до деплоя.

Основные понятия

  • Commit: зафиксированное изменение с метаданными.
  • Branch: независимая линия разработки.
  • Merge: слияние изменений из одной ветки в другую.
  • Remote: удалённый репозиторий (например, origin).

Почему это полезно

  • История изменений и откат на любой шаг.
  • Параллельная работа в ветках без конфликтов в основном коде.
  • Автоматизация тестов и деплоя через Actions.

Развернутый обзор функций GitHub

  • Репозитории: public/private, шаблоны, форки.
  • Issues & Projects: управление задачами, доски Kanban.
  • Pull Requests: обсуждения, ревью, CI — централизованный процесс вливания изменений.
  • Actions: workflow, matrix builds, deployment pipelines.
  • Packages: npm/Maven/Docker registry под управлением GitHub Packages.
  • Security: Dependabot alerts, code scanning, secret scanning.
  • Pages & Wiki: документация проекта и хостинг статических сайтов.
  • Organizations & Teams: управление доступом и политиками безопасности.

Pull Requests — руководство для команд

Что такое PR и зачем

PR — запрос на вливание изменений из одной ветки в другую с возможностью обсудить, протестировать и просмотреть код. Это ключевой элемент коллективного контроля качества.

Процесс открытия качественного PR

  1. Малые изменения: разделяйте работу на небольшие коммиты и логичные шаги.
  2. Чистый бранч: создавайте ветку от main: git checkout -b feature/short-name.
  3. Описание PR: поясните цель, изменения, как тестировать и потенциальные последствия.
  4. Автотесты: убедитесь, что CI проходит; прикрепите тестовые сценарии.
  5. Ревью: назначьте ревьюеров и отработайте комментарии.

Шаблон PR (пример)

# Title: Short description

## Что сделано
- Короткий перечень изменений

## Почему
- Причина изменений

## Как проверить
1. Шаги для локального тестирования
2. Ожидаемый результат

GitHub Actions — CI/CD и автоматизация

Actions позволяет запускать workflow на события: push, PR, schedule и др. Примеры: тесты, линтинг, сборка, релиз и деплой.

name: CI & Deploy
on:
  push:
    branches: [ main ]
  pull_request:
    branches: [ main ]
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Use Node.js
        uses: actions/setup-node@v4
        with:
          node-version: '18'
      - run: npm ci
      - run: npm test
  build_and_deploy:
    needs: test
    runs-on: ubuntu-latest
    if: github.ref == 'refs/heads/main'
    steps:
      - uses: actions/checkout@v4
      - run: npm ci
      - run: npm run build
      - name: Deploy to Pages
        uses: peaceiris/actions-gh-pages@v3
        with:
          github_token: ${{ secrets.GITHUB_TOKEN }}
          publish_dir: ./build

Советы по Actions

  • Кэшируйте зависимости (actions/cache) для ускорения билдов.
  • Разделяйте job'ы (test, build, lint) для параллелизации.
  • Минимизируйте секреты и давайте минимальные права токенам.

Релизы, пакеты и артефакты

Используйте Releases для публикации версии: теги, changelog, бинарные артефакты. GitHub Packages позволяет хранить пакеты (npm, Maven, Docker) рядом с кодом.

  1. Добавьте тег: git tag -a v1.0.0 -m "Release 1.0.0" и запушьте тег: git push origin v1.0.0.
  2. На GitHub — Releases → Draft a new release → выберите тег, добавьте changelog и прикрепите артефакты.

Организация репозитория и лучшие практики

  • README: подробный, с примерами установки и использования.
  • CONTRIBUTING.md: правила вклада, формат PR и code style.
  • CODEOWNERS: кто отвечает за какие части кода.
  • SemVer: придерживайтесь семантического версионирования.
  • Monorepo vs Multirepo: выбирайте исходя из команды и жизненного цикла пакетов.

Частые ошибки и как их исправлять

  • Ошибка: "remote rejected: file too large" — решение: использовать Git LFS или хранить файлы в релизах/артефактах.
  • Ошибка: конфликт при merge — решение: локально выполнить rebase/merge и разрешить конфликты, затем push.
  • Ошибка: случайный коммит секретов — решение: снять секреты с истории (git filter-repo или BFG) и инвалисдить ключи.
