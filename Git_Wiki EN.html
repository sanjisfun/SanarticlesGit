Quick intro to Git & GitHub

Git is a distributed version control system. GitHub is a service built on Git that provides a web interface, collaboration tools (PRs), issue tracking and integrations. Together they enable tracking changes, collaborating on features and automating tasks from testing to deployment.

Core concepts

  • Commit: a saved change with metadata.
  • Branch: an independent line of development.
  • Merge: combine changes from one branch into another.
  • Remote: a hosted repository (e.g. origin).

Why use them

  • History and ability to revert to any point.
  • Parallel work in branches without breaking main.
  • Automation via Actions for tests and deployment.

Detailed feature overview

  • Repositories: public/private, templates, forks.
  • Issues & Projects: task management and Kanban boards.
  • Pull Requests: code review, discussion, CI integration.
  • Actions: workflows, matrix builds, deployment pipelines.
  • Packages: npm/Maven/Docker registries via GitHub Packages.
  • Security: Dependabot alerts, code & secret scanning.
  • Pages & Wiki: documentation hosting and static sites.
  • Organizations & Teams: access control and policies.

Step-by-step: common scenarios

Create a repo and upload a project (git, full example)

# create project folder
mkdir my-project && cd my-project

# initialize repo
git init

# add files and initial commit
git add .
git commit -m "Initial commit"

# create repo on GitHub (via website) or with gh:
# gh repo create my-project --public --source=. --push

# add remote and push
git remote add origin https://github.com/USERNAME/my-project.git
git branch -M main
git push -u origin main

Handy short commands

# status
git status

# differences
git diff

# pull changes and rebase
git pull --rebase

# view compact log
git log --oneline --graph --decorate --all

Git LFS (for big files)

git lfs install
git lfs track "*.psd"
git add .gitattributes
git add large.psd
git commit -m "Add large asset"
git push
Tip: never commit secrets into the repo — use GitHub Secrets and .gitignore.

Pull Requests — a team workflow guide

What PRs are and why they matter

A PR is a request to merge changes from one branch into another, allowing discussion, review and CI checks. It's central to collaborative quality control.

How to open a high-quality PR

  1. Small changes: split work into small commits and logical units.
  2. Clean branch: create branch from main: git checkout -b feature/short-name.
  3. PR description: explain intent, changes, how to test and possible impact.
  4. Automated tests: ensure CI passes; include test instructions.
  5. Review: assign reviewers and address feedback.

PR template (example)

# Title: Short description

## What changed
- Bullet list of changes

## Why
- Motivation

## How to test
1. Steps to reproduce
2. Expected result

GitHub Actions — CI/CD and automation

Actions runs workflows on events: push, PR, schedule, etc. Typical uses: test, lint, build, release, deploy.

Advanced example workflow for Node.js: tests + deploy to GitHub Pages

name: CI & Deploy

on:
  push:
    branches: [ main ]
  pull_request:
    branches: [ main ]

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Use Node.js
        uses: actions/setup-node@v4
        with:
          node-version: '18'
      - run: npm ci
      - run: npm test

  build_and_deploy:
    needs: test
    runs-on: ubuntu-latest
    if: github.ref == 'refs/heads/main'
    steps:
      - uses: actions/checkout@v4
      - run: npm ci
      - run: npm run build
      - name: Deploy to Pages
        uses: peaceiris/actions-gh-pages@v3
        with:
          github_token: ${{ secrets.GITHUB_TOKEN }}
          publish_dir: ./build

Actions tips

  • Cache dependencies (actions/cache) to speed builds.
  • Split jobs (test, build, lint) for parallel execution.
  • Give minimal permissions to tokens and secrets.

Releases, packages and artifacts

Use Releases to publish versions: tags, changelogs, and attach binaries. GitHub Packages stores packages (npm, Maven, Docker) next to your code.

Creating a release

  1. Tag: git tag -a v1.0.0 -m "Release 1.0.0" and push: git push origin v1.0.0.
  2. On GitHub: Releases → Draft a new release → choose tag, add changelog, attach artifacts.

Repository organization & best practices

  • README: clear setup, examples and usage.
  • CONTRIBUTING.md: contribution rules, PR format, code style.
  • CODEOWNERS: who owns which parts of the codebase.
  • SemVer: follow semantic versioning.
  • Monorepo vs Multirepo: choose based on team and package lifecycle.

CODEOWNERS example

# Users or teams responsible for folders
/docs/ @docs-team
/src/ @frontend-team

CONTRIBUTING.md — short

# Contributing

1. Fork the repo
2. Create branch feature/your-feature
3. Add tests
4. Open PR with description and testing steps

Common issues & fixes

  • remote rejected: file too large — use Git LFS or upload as release artifact.
  • Merge conflicts — fetch latest main, rebase or merge locally, resolve conflicts, then push.
  • Accidentally committed secrets — remove from history with git filter-repo or BFG and rotate keys.
